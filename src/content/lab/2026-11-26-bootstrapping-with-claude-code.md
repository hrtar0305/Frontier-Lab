## 배경

이 사이트의 첫 Lab 글은 사이트를 만든 과정 자체다. 바탕화면의 빈 폴더에서 시작해 리포지토리 생성, 사이트 뼈대, 배포까지를 Claude Code 한 세션에 맡겼고, 그 과정에서 사람이 개입해야 했던 지점을 기록한다.

코드를 짜는 일과, 계정·리포지토리·배포처럼 코드 바깥의 일을 처리하는 것은 다른 문제다. 이 글이 보려는 것은 뒤쪽이다.

## 환경

- 날짜: 2026년 11월 26일
- Windows 11, Claude Code 데스크톱 앱, 모델은 Claude Fable 5.2
- Git 2.55, Node.js 24.20.0, npm 12.2.2. GitHub CLI(`gh`)는 설치되어 있지 않았다.
- GitHub 인증 정보는 Git Credential Manager 에 저장된 상태였다.

## 과정

사람이 직접 쓴 요청은 두 개였다(리포지토리 만들기, 큰 그림 제안). 나머지는 모두 에이전트가 내민 질문에 답한 것이다.

### 1. 리포지토리 만들기

요청은 "GitHub 계정을 확인해서 리포지토리를 만들고, clone 한 뒤 프로젝트 폴더를 그쪽으로 옮겨 달라"였다. 목적은 AI 트렌드를 따라가며 공부하는 사이트라고만 알려 줬다.

**권한에서 한 번 멈췄다.** `gh` 가 없어서 에이전트는 Git Credential Manager 에 저장된 토큰을 꺼내 GitHub REST API 를 호출하려 했고, 앱의 권한 검사가 이 명령을 차단했다. 에이전트는 다른 방법으로 토큰을 꺼내려 하지 않고 멈춰서 세 가지를 물었다.

- 브라우저 창에서 직접 로그인해 주면 양식을 채우겠다
- 저장된 토큰 사용을 허용해 달라
- 직접 만들어 주면 그 뒤를 이어 가겠다

토큰 사용을 허용하자 같은 호출이 통과했고, 리포지토리가 만들어졌다.

**이름에서 두 번 퇴짜를 놨다.** 첫 후보는 `ai-trend-study` 같은 설명형, 두 번째는 `NextToken` 같은 말장난형이었는데 둘 다 마음에 들지 않았다. "나만 보는 것이 아니라 남도 보고, 포트폴리오이기도 하고, 직접 실험한 결과를 계속 쌓을 것이니 장기적으로 쓸 이름"이라는 기준을 준 뒤에야 `Frontier-Lab` 이 나왔다. 처음 요청에 이 기준이 없었으니 후보가 빗나간 것은 당연했다.

### 2. 방향 정하기

"어떻게 진행하면 좋을지 큰 그림을 제안해 달라"고 했다. Radar·Notes·Lab 세 구역과 4단계 진행안이 나왔고, 그대로 받아들였다. 자동화를 뒤로 미루자는 것도 에이전트의 제안이었다.

### 3. 사이트 뼈대 만들기

**모르는 버전은 읽고 썼다.** npm 에 올라온 Astro 최신 버전은 7.4.13 이었다. 에이전트는 자기가 아는 것보다 새 버전이라며 기억으로 코드를 쓰지 않았다. 공식 블로그 템플릿을 임시 폴더에 받아 현재 코드를 읽고, 그 방식(`src/content.config.ts`, `astro/loaders` 의 `glob`, `astro/zod`)에 맞춰 작성했다. 배포 워크플로에 들어가는 액션 버전도 공식 문서 페이지를 열어 확인했다.

**조사는 따로 떼어 병렬로 돌렸다.** Radar 첫 글에 넣을 최근 소식 조사는 하위 에이전트에 맡기고, 그동안 주 에이전트는 사이트 파일을 썼다. 하위 에이전트에 준 조건은 "직접 연 1차 출처가 있는 것만, 날짜는 출처에 적힌 것만"이었다. 5건이 채택됐고 확인하지 못한 것은 따로 구분되어 돌아왔다. 주 에이전트는 채택된 5개 주소를 다시 열어 제목과 날짜를 대조했다.

**판정은 비워 뒀다.** Radar 항목의 "써 볼 것인가"는 운영자가 정할 일이라며, 에이전트는 판정을 채우지 않고 그 글을 초안 상태로 남겼다.

### 4. 확인하기

- **빌드와 타입 검사.** `astro build` 는 8쪽을 만들었고(초안인 Radar 글은 빠진다), `astro check` 는 파일 18개에서 오류 0건이었다.
- **화면.** 개발 서버를 띄우고 라이트·다크 화면과 375px 폭을 직접 열어 봤다. 여기서 두 가지를 고쳤다. 고정폭 글꼴을 쓴 라벨에서 한글이 굴림체로 떨어지던 것, 그리고 첫 화면 카드에 구역 이름이 두 번 나오던 것이다. 둘 다 빌드나 타입 검사로는 잡히지 않는다.
- **도구가 한 번 어긋났다.** 세션 도중에 작업 폴더를 새 리포지토리로 옮겼더니, 앱의 미리보기 도구가 이미 지운 예전 폴더에서 설정 파일을 찾다가 실패했다. 에이전트는 Astro 의 백그라운드 개발 서버(`astro dev --background`)로 바꿔 확인을 이어 갔다.

### 5. 배포하기

GitHub Pages 를 켜는 설정은 리포지토리를 만들 때와 같은 방식(저장된 토큰으로 REST API 호출)으로 처리됐다. 그 뒤 `main` 에 푸시하자 GitHub Actions 가 빌드와 배포를 실행했고, 첫 실행에서 성공했다. 에이전트는 배포된 주소를 직접 열어 첫 화면과 글 페이지가 뜨는지, 초안인 Radar 글의 주소가 404 로 나오는지 확인했다.

## 결과

사이트는 [hrtar0305.github.io/Frontier-Lab](https://hrtar0305.github.io/Frontier-Lab/) 에 올라갔다. 8쪽짜리 정적 사이트, 글 양식 3종, 배포 워크플로가 만들어졌다.

사람이 한 일은 다음이 전부다.

| 구분 | 내용 |
| --- | --- |
| 직접 쓴 요청 | 리포지토리를 만들어 달라, 큰 그림을 제안해 달라 |
| 질문에 답한 선택 | 공개 범위(Public), 토큰 사용 허용, 리포지토리 이름, 빈 폴더 삭제, 진행안 승인 |
| 반려 | 리포지토리 이름 후보 두 차례 |
| 직접 쓴 코드 | 0줄 |

반대로 에이전트가 묻지 않고 정한 것도 많다. 리포지토리 설명 문구, 한국어로만 쓴다는 것, Astro 라는 선택, 색과 글꼴, 글의 항목 구조, 그리고 이 글을 포함한 첫 글들의 문안이다.

## 관찰한 것

- **멈춘 곳은 권한과 취향이었다.** 에이전트가 사람을 부른 것은 토큰 접근이 막혔을 때와 이름처럼 정답이 없는 것을 정할 때였다. 기술적인 문제로 사람을 부른 일은 없었다.
- **요청에 없던 기준은 결과에도 없었다.** 이름 후보가 두 번 빗나간 것은 "오래 쓸 포트폴리오"라는 기준을 처음에 말하지 않았기 때문이다. 기준을 말한 뒤에는 한 번에 정해졌다.
- **확인 단계에서만 잡히는 것이 있었다.** 한글 글꼴 문제는 빌드도 타입 검사도 통과했다. 화면을 직접 열어 봤기 때문에 잡혔다.
- **묻지 않고 정한 것은 읽어 봐야 한다.** 위에 적은 대로 에이전트가 혼자 정한 것이 많다. 결과물이 돌아간다는 것과 그 선택들이 마음에 든다는 것은 별개다.

## 남은 질문

- 에이전트가 모아 온 Radar 초안은 실제로 쓸 만한가. 원문을 직접 읽고 판정을 채워 봐야 안다.
- 몇 주 운영한 뒤에도 이 구조와 주기가 유지되는가.
